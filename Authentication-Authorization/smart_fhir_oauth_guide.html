🏥 SMART on FHIR OAuth Flow

Understanding Authorization When Provider is Already Logged In

🏨 Hospital Badge Analogy

🏥 Real World

Dr. Smith is already wearing his hospital badge and working at his computer. A new medical app needs access to patient John's records. Instead of asking Dr. Smith to show his ID again, the hospital security system recognizes him and just asks: "Do you want to give this app access to John's data?"

💻 Technical Reality

Provider is logged into Epic EHR with an active session. When a SMART app launches, Epic recognizes the existing session and skips the login screen, going straight to the authorization/consent step (if required).

🔄 SMART on FHIR Flow (Provider Already Logged In)

1
🏥 Provider Session Exists
Dr. Smith is logged into Epic EHR, viewing Patient John's chart. Epic knows: • Provider identity (Dr. Smith) • Current patient context (John's ID) • Current encounter context
2
🚀 EHR Launch
Epic launches the SMART app with launch parameters: • iss=https://epic.hospital.com/fhir (FHIR base URL) • launch=abc123token (context token containing patient/encounter info)
3
🔐 Authorization Request
SMART app builds OAuth request and redirects to Epic's authorization endpoint with: • PKCE challenge • Launch token • Requested scopes (patient/Encounter.read, etc.)
4
✅ Session Detection (Key Difference!)
Epic detects Dr. Smith's active session and skips the login screen! May show consent screen if scopes require explicit approval, otherwise redirects immediately.
5
🎟️ Authorization Code
Epic redirects back to the SMART app with: • Authorization code • State parameter (for security) This happens almost instantly due to existing session!
6
🔄 Token Exchange
SMART app exchanges authorization code for access token using PKCE verifier. Receives access token + patient/encounter context information.
7
📊 Access Patient Data
SMART app uses access token to fetch Patient John's data: • GET /Patient/{john-id} • GET /Encounter/{encounter-id} • Other FHIR resources as authorized

🔑 Key Insight: The SSO Effect

When the provider is already logged in, the OAuth flow feels seamless because:

  • No password prompts - Epic reuses the existing authenticated session
  • Context is preserved - Patient and encounter information flows automatically
  • Faster authorization - Skips the most time-consuming step (user login)
  • Better user experience - Feels like a native EHR feature rather than external authentication
Example Authorization Request URL:

https://epic.hospital.com/oauth2/authorize?
  response_type=code&
  client_id=smart-app-123&
  redirect_uri=https://smartapp.com/callback&
  scope=launch/patient patient/Encounter.read openid fhirUser&
  state=random-security-string&
  aud=https://epic.hospital.com/fhir&
  launch=abc123token&
  code_challenge=pkce-challenge&
  code_challenge_method=S256

🏨 Hospital Security Check Analogy

🏥 Real World

Dr. Smith arrives at the hospital without his badge. When he tries to access a patient's records through a medical app, security first asks him to show his ID and prove he's authorized to be there. Only after verification can he access the patient data.

💻 Technical Reality

Provider has no active Epic session. When the SMART app launches, Epic must first authenticate the provider (username/password or SSO) before proceeding with the OAuth authorization flow.

🔄 SMART on FHIR Flow (Provider Not Logged In)

1
❌ No Active Session
Dr. Smith is not logged into Epic. The EHR system has no knowledge of the provider's identity or current patient context.
2
🚀 EHR Launch (Limited)
Epic may launch the SMART app, but without full context: • iss=https://epic.hospital.com/fhir • Launch token may be limited or absent
3
🔐 Authorization Request
SMART app builds OAuth request and redirects to Epic's authorization endpoint (same as logged-in scenario)
4
🔑 Login Required (Key Difference!)
Epic detects NO active session and shows login screen first! Dr. Smith must enter username/password or use SSO before proceeding.
5
✅ Authentication Complete
After successful login, Epic establishes the provider's session and identity. Now Epic knows who Dr. Smith is and his permissions.
6
📋 Consent/Authorization
Epic may show consent screen for the requested scopes. Provider approves access to patient data for the SMART app.
7
🎟️ Authorization Code
Epic redirects back to SMART app with authorization code and state parameter. This step is identical to the logged-in scenario, but took longer to reach.
8
🔄 Token Exchange
SMART app exchanges authorization code for access token using PKCE verifier. (Same as logged-in scenario)
9
📊 Access Patient Data
SMART app uses access token to fetch patient data. Final outcome is the same, but the journey was longer!

⏱️ Time & User Experience Impact

When the provider isn't logged in, the flow takes significantly longer because:

  • Additional authentication step - User must enter credentials
  • Context loss risk - May lose current patient/encounter context
  • Workflow interruption - Provider must stop current task to authenticate
  • Security friction - Additional verification steps slow down the process

🏨 Complete Hospital Analogy Comparison

🟢 Badge Already On (Logged In)

Scenario: Dr. Smith is at his workstation, badge visible, treating Patient John. A new diagnostic app needs John's lab results.

Process: Security guard sees the badge, recognizes Dr. Smith, and immediately asks: "This app wants John's lab data. Approve?" Dr. Smith clicks "Yes" and gets instant access.

Result: ⚡ 5-second process, no workflow interruption

🟡 No Badge (Not Logged In)

Scenario: Dr. Smith arrives at the hospital, no badge visible, wants to use the same diagnostic app for Patient John.

Process: Security guard stops him: "Show me your ID first." Dr. Smith finds his badge, scans it, enters PIN, proves identity, then gets asked about app permissions.

Result: ⏳ 60-second process, significant interruption

🎯 Why This Matters in Clinical Practice

The difference between these scenarios significantly impacts healthcare delivery:

✅ When Provider is Logged In:

  • Seamless integration - Apps feel like native EHR features
  • No workflow interruption - Clinical decision-making continues
  • Better patient care - Providers can access tools instantly
  • Context preserved - Patient and encounter data flows automatically
  • Higher adoption - No friction means providers actually use the apps

⚠️ When Provider Must Log In:

  • Workflow disruption - Must stop to authenticate
  • Context switching - May lose focus on current patient
  • Time pressure - Additional delays in urgent situations
  • User frustration - Authentication fatigue leads to workarounds
  • Lower adoption - Friction discourages app usage

🔧 Technical Implementation Notes

For developers implementing SMART on FHIR apps:

  • Session detection: Epic automatically detects active provider sessions
  • Launch context: The launch token contains patient/encounter IDs when provider is logged in
  • Error handling: Apps should gracefully handle both scenarios
  • User feedback: Show loading states during authentication flows
  • Context recovery: Store minimal state to recover from authentication interruptions
